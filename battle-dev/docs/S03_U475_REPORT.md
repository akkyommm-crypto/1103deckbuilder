## 欠陥の仕組み（U472 で TGX3－DX2 に見つかったものの一般化）
`v70SelectExactly`（`cards/70_v70_autobuild_batch22.js` の定義）と `v380SelectExactly`（`cards/38_1103_expansion_v380.js`）の違いは**返す値の形**だけ。
| | 返す値 | チェーンを通った後 |
|---|---|---|
| 旧 `v70SelectExactly` | `{card}`（`p` / `zone` / `index` なし）の配列 | 複製 |
| `v380SelectExactly` | 選択の候補 `t` そのまま（`p` / `zone` / `index` / `card`） | 元のカード |

`serializeChainSelectionV2`（`engine/00_state_actions.js:2835`）は **`v.card && typeof v.zone==='string' && v.p!=null`** の値だけをカード参照（uid ＋ゾーン、`cardRef`）に置き換える。`{card}` はこの条件を満たさないので「普通のオブジェクト」として再帰コピーされ、`card` の中身がカードの**複製**として `link.targets` に保存される（`deserializeChainSelectionV2` は複製をそのまま返す）。解決時に効果が `resolveTarget({card:複製})` を呼ぶと、`engine/40_legal_script_engine.js:742` は `locateCard` と各ゾーンの `indexOf` で**同一性**で探すので見つからず `null`。効果の「対象に依らない部分」（`API.shuffle` / `API.draw`）だけが動き、選んだカードは何も動かない。

選択結果が **チェーンに載る**のは `target` フックで使った時だけ（`ctx.selectedTargets` へ）。`cost` フックで使うとその場（同じコールバック内）で処理され、複製を経由しないので影響を受けない。

## 修正（`cards/70_v70_autobuild_batch22.js` の定義 1 行）
U472 は呼び出し側を `v380SelectExactly` に差し替えたが、本単位は**ヘルパの定義側を直した**。
- `v70SelectExactly` は選択の候補 `t` をそのまま集めて `done` に渡す（`v380SelectExactly` と同じ形。タイトルの書式 `title 1/n` は従来のまま）。フィルタは `chosen.some(y=>y.card===x.card)`。
- **理由**: 呼び出し側 18 か所を `v380SelectExactly` に差し替えると、既存の 2 つのソース文字列ピン `tools/test_v740_batch26.js`（`'exact two selection'`: `source.match(/v70SelectExactly/g).length>=3`）と `tools/test_v750_batch27.js`（`'exact recovery selection'`: `source.includes('v70SelectExactly')`）が FAIL する（実測: 各 1 FAIL）。これらは「その `cards/` ファイルがこの正確選択ヘルパを使う」ことを見張る期待で、欠陥の挙動を符号化したものではないが、ワークフロー v3 ではテスト期待の変更は私の権限外。定義を直せば 18 枚すべて（と将来の利用者）が一度に直り、既存テストは無変更で通る。**呼び出し側を差し替える案が良ければ、その 2 件のピンの更新承認が要る**（この選択は戻せる）。
- `cost` フックの 3 か所（4 枚）も戻り値の形が変わるが、`resolveTarget(t)` が `t.card` を `indexOf` で引くだけなので結果は同じ（新テストで 4 枚とも実測）。
- 呼び出し側の 18 行は無変更。定義の上にコメント 2 行（原因と U472 への参照）を追記。
