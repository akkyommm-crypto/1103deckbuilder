# 「タイミングを逃す」の設計（共通エンジン課題）

S03-U487 / U488 / U489 が未解決として残した「チェーン2以上で召喚し、その後に別の処理がある場合はタイミングを逃す」を、
カード個別の対処ではなく共通処理として入れるための設計。**本書は設計のみで、実装は S03-U491 以降で段階的に行う。**

## 3. 設計

### (A) 処理ステップ番号 `procStepS03`

`gameState.procStepS03` を単調増加のカウンタとして持ち、**`act()` の最上位の適用 1 回を 1 ステップ**とする
（`APPLY_ACTION_DEPTH_V31` が 0 → 1 になる所で増やす）。

- 1 回の `act()` の中で起きたことは**同時**。そこで積まれた誘発は互いを逃させない（R4）
- 解決の途中で別の `act()` が走れば、先に積まれた誘発は「その後に処理があった」ことになる（R2）
- チェーンの残りリンクの解決は多数の `act()` を伴うので、R3 は自動的に満たされる

ただし帳簿用の Action（`EVENT_QUEUE_V31` / `CHAIN_ADD` / `CHAIN_RESOLVE_TOP` / `EVENT_DEQUEUE_V31` /
`SUMMON_WINDOW_OPEN_V42` 等）はステップを進めてはいけない。**除外リスト**で扱う
（包含リストより小さく、取りこぼした場合に「逃さない」＝現状維持側に倒れるため安全）。
`act()` の呼び出し箇所から拾った Action の種類は **103 種**。そのうち帳簿・提示・掃除に相当する候補は
次の 26 種で、S03-U491 で 1 件ずつ検討して確定させる（迷ったものは「進める」側に置かない＝現状維持に倒す）。

```
ATTACK_PENDING_CLEAR_S03, CHAIN_ADD, CHAIN_CLEAR, CHAIN_NEGATE_LINK, CHAIN_RESOLVE_TOP,
CHAIN_RETARGET_S03, CHOICE_ANSWER_V49, CHOICE_CANCEL_V49, CHOICE_OPEN_V49, COUNTER_CLEAR,
EVENT_DEQUEUE_V31, EVENT_QUEUE_V31, EVENT_RESUME_V11, EVENT_SUMMARY_S03, EVENT_TAKE_S03,
EX_SUMMON_PREPARE_V42, LINK_CLEAR_V9, MOD_CLEAR, MOD_CLEAR_LABEL_V7, PREP_TX_ABORT_S03,
PREP_TX_BEGIN_S03, PREP_TX_COMMIT_S03, SET_PRIORITY, SUMMON_WINDOW_CLOSE_V42,
SUMMON_WINDOW_NEGATE_V42, SUMMON_WINDOW_OPEN_V42
```

確定は R1 の実測（下記 5）で行う。「宣言 0 件」の段階では除外リストの誤りが対局に出ないので、
実際の対局ログでステップ番号の進み方を観測してから宣言を始める。

### (B) 「時」／「場合」と例外の宣言（データ）

`data/missed_timing_overrides.json` にカード名 → `{"mode":"miss"|"never","ruling":"WIKI-…","note":"…"}`。

- **宣言の無いカードの既定値は `never`**（＝現在の挙動）。根拠の無いカードの挙動を勝手に変えない
- カードテキスト（`data/carddata.json` の `e`）からの自動推定は**採らない**。
  DB のテキストは時代が混在しており（《代打バッター》は現行の「①:…時に発動できる」、
  《E・HERO The シャイニング》は当時の文面）、推定の誤りが静かに対局を変える
- 段階導入: 1 章の裁定を持つカードから順に宣言していく

### (C) 判定は `collectHandlers` の 1 箇所

誘発候補を 1 件落とす条件は次の 3 つが同時に成り立つとき。

1. その誘発の元イベントに刻まれた `stepS03` が、いま提示しようとしている時点の `gameState.procStepS03` と**異なる**
2. その候補が**強制ではない**（`triggerCandidateForcedS03(c) === false`）
3. そのカードが `missed_timing_overrides.json` で `miss` と宣言されている

落としたことは対局ログに残す（「タイミングを逃した」）。落とした結果候補が 0 件になれば、
`emitEvent` は `false` を返して従来どおり次へ進む。

## 4. 保存・再開・Replay

- 各 `deferredEvents` 項目に刻む `stepS03` は、`v41StateDigest` が既に
  `JSON.stringify(g.deferredEvents||[])` を含んでいる（`engine/06:142`）ので**自動的に digest に入る**。
  誘発が積まれている局面の digest は変わるが、**literal な digest を固定している既存テストは 0 件**、
  `data/` に保存済み Replay パッケージも無いので、既存の比較（保存なし ⇔ 再開 ⇔ Replay）はそのまま成立する
- `gameState.procStepS03` 自身は digest に**追記しない**。Action の適用順から決まる導出値であり、
  Journal 再生でも同じ値に再構成される。`timingWindow` を digest に入れない方針（S03-U486 / U489）と同じ扱いで、
  かつ判定に使うのは「刻んだ値と現在値が等しいか」という差分だけなので一致する
- 保存は `gameState` をまとめて直列化するので `procStepS03` も保存に乗る。
  再開直後にだけ値がずれる余地が無いことを、S03-U489 と同じやり方（再開の末尾で実測）で確認する
- `EVENT_QUEUE_V31` の payload に `stepS03` を入れるので、Journal 再生でも同じ値が再現される
- 回帰テストは S03-U484 と同じ 3 本立てにする:
  1. 保存なしで通しで駆動した場合の候補列
  2. 停止点で保存 → 新しい VM で再開した場合の候補列（**1 と一致すること**）
  3. `v44ReplayAuditPackage` の監査（全 digest と最終状態の再現）
  さらに negative control（判定を無効化すると逃さなくなる＝元の挙動に戻る）

## 6. 採らない案

- **カードごとに個別実装する**: 同じ規則が 100 枚以上に散り、保存・再開の一致も個別に壊れる
- **テキストからの自動推定だけで全カードに適用する**: 上記 (B) の理由。根拠の無い挙動変更になる
- **チェーンリンク番号だけで判定する**: R4 の《光神テテュス》08/01/30（チェーン1が「処理なし」なら逃さない）を
  説明できない。判定軸は「最後に行われた処理か」であって、リンク番号ではない
