# S03-U497 報告：召喚そのものの無効の窓 — 処理順の実測と設計の確定（挙動の変更なし）

対象は `docs/S03_MISSED_TIMING_DESIGN.md` 5-a #1 に残していた「召喚そのものの無効」。
**先に設計を決めず、窓がいまどこで開くかを実測した。**結果として、想定していた設計は誤りだと分かった。

本単位は **挙動を変えていない**。変えたのは文書・engine のコメント・テストだけである。

| 実測 | 結果 |

| 候補カードの全件（`sc.summonNegate`）| **14 枚**。通常召喚に応答できるのは 10 枚 |
| `beginSummonWindowV2` の呼び出し元 | **5 か所・4 種別**（`normal` / `flip` / `procedure` / `synchro`・`xyz`）。すべて UI 操作が起点 |

## 2. 想定していた設計が誤りだった

「`SUMMON_WINDOW_*` へ (A) の処理番号の比較を入れれば、召喚無効もタイミングを逃す」という形は
**採れない**。既存の窓は必ず `procStepS03` 0 の時点で開くので、比較は一度も成立しない。
入れても挙動は変わらず、「召喚無効も逃すようにした」という**誤った記録だけが残る**。

「保留イベントが空であることを条件にする」案も採れない。シンクロ召喚の窓は保留イベント 4 件
（素材が場を離れた分）を抱えて開くので、この案では EX 召喚が常に無効にできなくなる。
素材の離脱はシンクロ召喚の手順そのもので、当時裁定の言う「召喚の後の別の処理」ではない。

## 3. 本当の食い違いは逆向きだった

`WIKI-2CF23AA42E79`（**回答日 2011-08-25**、掲載ページ《血の代償》）は
「チェーン１で行われているならば、発動可能です。チェーン２以上で行われ、召喚の後に別の処理がある場合は
タイミングを逃す事になり発動できません。」と答えている。

- **チェーン1** — 当時は《神の宣告》《キックバック》《昇天の角笛》を**発動できる**。
  いまのエンジンは窓を開かないので、**当時できる発動を潰している**。
- **チェーン2** — 当時は逃す。いまのエンジンの結果は一致するが、**規則としてではなく窓が無いだけ**である。

つまりチェーン2 側の「正しさ」は偶然で、チェーン1 側は誤りだった。

## 4. 確定した設計（(D)）と、実装を入れなかった理由

判定を入れる場所は既存の窓ではなく「解決中の召喚のあと、チェーンが終わった時点」になる。

- **刻む** — 解決中に召喚が行われたとき、その時点の `procStepS03` と再開データを `gameState` に記録する。
- **開く** — `processChainEndV30` で、`procStepS03` が刻んだ値と**同じ**なら窓を開く。違えば記録を捨てる
  （＝いまと同じ挙動。逃す）。窓の中身・保存・Undo は既存の `pendingSummon.resumeS03` に乗せる。

実装は入れていない。測って分かった障害が 2 つあり、どちらも**公開済みの経路**に触るためである。

1. チェーン終了の時点で召喚はもう盤面に適用されている（実測：《ワイト》はモンスターゾーンに居り、
   `onNormalSummon` は保留列の最後）。既存の commit 経路は「カードは手札にある」前提。
   解決中に召喚しない形（案 (a)）にするとチェーン2 の刻み方が変わり、**公開済みの (A) の実経路が動く**。
2. `processDrainEventsV27` に `pendingSummon` を見る条件が無い。窓を開いただけでは `onNormalSummon` が
   窓より先に排出され、《奈落の落とし穴》等が無効より先に出る。

第一候補は案 (b)（召喚はそのままにし、無効のときだけ盤面から取り除いて保留列の `onNormalSummon` を落とす）
だが、永続効果が一瞬適用される近似になり「破壊された時」の扱いも別に決める必要があるので、
**設計として記録するだけ**にした。
