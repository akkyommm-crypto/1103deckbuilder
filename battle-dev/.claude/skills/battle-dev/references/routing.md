# 役割分担と比較

## 担当を選ぶ
Sonnet通常担当 → 既存APIに収まらない点・裁定不明・共通処理不具合があればOpus → 共通処理と検証方針が定まったらSonnet。
メインが適切なモデルなら直接実行し、同じモデルの委譲を増やさない。常時2人を動かす方式ではない。
現セッションがOpusなら、通常作業をSonnetへまとめて委譲して戻りを確認する。各ツール実行を逐一報告しない。

委譲：目的、ツリー・基点、変更可能範囲、参考実装1〜2件、期待結果、テスト、ゲート担当。
返却：差分・判断根拠・再現手順・テスト結果・未解決点。引き継ぎコストも消費に含める。

Sonnet/Opusのエイリアスはプロバイダーや設定で別世代に解決される場合がある。
初回に実際のモデル名を確認する。指定の5.5が使えなければ明示し、別モデルで同じ比較条件を満たすと言わない。
使用中のClaude Codeとモデルがeffortフィールドに対応していることも確認する。権限は緩めない。

## 節約の比較
同じカテゴリで、Opus単独と分担を各3〜5単位程度から試す。少数例は傾向を見るだけ。
カテゴリは着手時に固定：reuse（既存機能の再利用）、engine（共通処理）、ui（見た目・操作）。受入条件も事前に決める。
通常業務の同程度の単位を交互に割り当てる。比較のためだけに同じ実装を2回行って消費を増やさない。
カード枚数やPASS行数は難しさを表さない。共通処理の有無や対象範囲が違えば別に集計する。

`measurements/record.example.json` を別名でコピーし、exampleをfalseにして1単位1JSONで記録する。
- 実際のモデルとeffort。主担当だけでなく全サブエージェントを含む。
- 経過時間（テスト待ちを含む）。他作業・中断が混じれば備考へ。
- やり直し回数：最初の検証失敗以後、実装修正して再検証した回数。単純再実行は別記する。
- 全体ゲート結果、受入条件の達成、後から見つかった不具合。
- モデル別の入力・出力・キャッシュ読込・キャッシュ作成トークン。取得元と集計範囲。

`/usage`等の実測値を使う。開始・終了の差分では、途中のセッションリセットや別タスク混入に注意。
子を含む親の集計へ子の消費を再加算しない。集計範囲が不明なら未計測とする。
コスト、総トークン数、月額プランの週制限は別。削減率が同じになると断定しない。

`scripts/compare.py <記録フォルダ>` はカテゴリ・方式別に集計する。未計測は0で埋めず、全件計測できない群は合格1単位あたりトークンを出さない。
失敗単位も消費に含める。品質を落として数字を良くしない。受入後の不具合は該当記録を更新する。

## リアルタイム表示
「Sonnetが実装中／Opusに相談／テスト待ち」は作業状態。「合格1単位あたり消費」は結果の比較。
まず `/tasks` と `/usage` を利用し、常駐AIを監視役にしない。
自動トークン表示が必要なら公式OpenTelemetry連携等を検討する。外部送信・collector設定は本パッケージに含めない。
既存battle_progress.htmlは対応状況のスナップショットで、AI稼働・消費量を自動取得しない。
