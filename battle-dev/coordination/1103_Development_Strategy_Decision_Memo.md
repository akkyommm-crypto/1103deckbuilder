# 1103 Duel Simulator — Development Strategy Decision Memo

監査日：2026-09-10。対象：System02 clean checkpoint。

## 1. Executive Decision

**採用する方式は「実戦の阻害要因を優先するCapability単位の開発」です。既存エンジンを維持し、カード・不足機能・検証証拠を結ぶ薄い分析層を追加します。代表デッキは優先順位と受入判定に使います。**

開発の基本単位を「次のカード数枚」から、**「共通の不足を一つ閉じ、複数カードの実際の操作経路を通す一つの変更」**へ変えます。既存機能だけで書けるカード群は、その契約が一致する範囲でまとめて処理します。

今すぐ全面rewrite、全カードのDSL化、36 moduleの再配置は行いません。実コードには再利用可能なAction、Processor、Choice、Unified Effect、UID装備リンク、Replayがあり、System02は既存の供給元と攻撃判定の接続だけで2枚を解禁しています。資産を捨てる利益は、今回の証拠からは立証できません。

ただし現状を完成に十分なエンジンとも判定しません。Capabilityの契約を明示し、実際の入口から出口まで不足を確認した箇所だけを拡張します。主要デッキの完走を早期のリリース目標とし、その後も同じ方式で全4996枚の要件を閉じます。

- coverageの全4996行、旧監査の全620行との対応、選定・coverage・gateのコード、主要エンジン接続、System01/02と直近cycleのカード・テストを調査。
- ZIP内の全回帰ログは11458 PASS／0 FAIL。これは保存された実行結果であり、今回の全回帰再実行結果ではありません。

添付内の過去の作業指示・次System推奨は監査対象です。今回のユーザー依頼にある「実装禁止」を優先しました。

## 2. Why Development Is Slow

以下は重要度順の診断です。時間計測に基づく寄与率ではなく、実装から確認した作業構造と、その影響の判断です。

### ① 選定と学習がつながらず、以前の調査を再利用できない

`select_script_batch.py` は通常 `NOT_STARTED` のみを候補とし、デッキ掲載・テキスト由来の複雑さ等で並べます。標準では複雑さ45超を除き、`PARTIAL` は任意指定、`ENGINE_GAP` と `IMPLEMENTED` は回収対象に入りません。手動でSystem開発を挟めても、自動選定の目的関数は依然として「次に書きやすいカード」です。

一方で、旧監査JSON、primitive分析、recoveryカード群、AI packは既に存在します。したがって問題は分類ツールの不在ではなく、**分析結果・能力の更新・次の仕事が機械的に連動していないこと**です。

### ② ENGINE_GAPが、現在の不足を表す依存関係になっていない

旧監査には27分類ありますが、主原因を1枚1分類に割り当てたものです。`astra_gap_audit.py` は620件をassertし、明示分類にCycle66の並び番号を使います。現616件を継続更新する仕組みとして、そのままは使えません。

実際、現在のgap理由には「first-class Ritual Summon pipelineが必要」が残る一方、`14_ritual_v5.js` と儀式テストは存在します。これはそのカードが既に完全実装可能という意味ではありません。**既存機能・未対応の変種・古い記述を再度切り分けなければ、理由を開発指示として使えない**という意味です。

### ③ 完了指標と、ユーザーが必要とする完了が離れている

現在の静的scannerは、原則として登録があり、除外対象以外のテストファイル中にカード名が含まれると `TESTED` にします。明示overrideが優先されます。専用テストの除外表やSystem02の誤昇格監査は良い対策ですが、カード名出現だけでは、全効果・召喚条件・timing・保存再開の検証範囲は分かりません。

例としてCycle66テストは、場に直接置いたカードの `condition / selectTargets / resolve` を呼び、回数制限の値を確認しています。このテストは効果処理の検査として有用ですが、正規の召喚、発動手続、チェーン、実際の2回目発動拒否を通した証明ではありません。System01/02には実経路のテストがあり、品質が一様ではありません。

また `script_coverage.py` の「Fully covered」集計は `IMPLEMENTED` も含めています。これを完成率に用いると、未検証作業が見えにくくなります。

### ④ Capabilityの境界より、ファイルと実装履歴をたどる必要がある

エンジンは36ファイルですが、Action約2994行、legality約1757行、processor約1518行など複数の大きな処理中心があります。manifest順の結合と共有関数で動き、独立moduleの集合ではありません。

System02でも、カード宣言 → continuous sourceの有効性 → 装備先到達性 → 攻撃上限 → 攻撃Processorまで確認が必要でした。1ファイルに機能名があっても、他の入口やconsumerまで対応した証拠にはなりません。境界の不明確さは調査負担を増やします。ただしファイルを移動するだけでは、この意味上の接続は減りません。

### ⑤ 局所修正に、過去の進捗記録を修理する仕事が付く

System02で過去のbatch28テストに解禁例外を追加しています。現行status監査にも2049／616／1307の固定値assertがあります。最新の変更範囲を保証する役割は有用ですが、過去の「まだgapである」という記録を永久に現行状態へ要求すると、正常な進捗でも旧テスト修理が発生します。

Cycle62–66はそれぞれ2〜5枚の追加でも全回帰とcheckpointの報告が伴っています。`check.py` には静的に209個のNode起動箇所があり、構文検査も含まれます。テスト数やログ量は実行時間そのものではないため、全回帰が最大の遅延原因とは断定しません。まず実測が必要です。

### ⑥ 裁定・context・handoffの再調査費用を管理できていない

AI packの固定ファイル一覧は存在しますが、能力の依存関係とテストから導出する仕組みではありません。DBの本文と自由文reasonを読むだけでは、その記述の歴史版・出典・判断済み範囲を追えません。

モデル間の入出力token、cache、修正往復、裁定調査時間の対照実測は添付から得られませんでした。「強いモデルが高すぎる」「handoffが主因」とまでは結論しません。**再調査の単位を小さくし、同じ判断を再利用できるようにする方が先**です。

## 3. Keep

- **既存engineとcard scripts。** 動作が証明された経路を維持し、不足に接する箇所だけを改修します。
- **Action／ProcessorとJSONで表現する状態。** 新しいゲーム状態の変更は、既存の記録・復元境界へ接続します。
- **UID、owner/controller、装備リンク、continuous source判定。** System01/02の局所拡張を可能にした基盤です。
- **Unified Effectとlegacy adapter。** 既に効果の宣言形式と互換層があるため、もう一つの実行言語を急いで作りません。
- **既存回帰テスト、Replay/RNG/digest、Undo/Redo、SaveLoadテスト。** 静的検査も役割を限定して残し、動作検査の証拠と区別します。
- **単一HTMLの配布方式、再現可能なbuild、clean checkpoint。** 配布単位は保ち、カード1枚を進める単位との結び付きを弱めます。
- **過去の分析と履歴。** 消去せず、基準checkpointと適用範囲を明示して再利用します。

## 4. Change

1. 次カード選択を、**未完了シナリオ → 原因契約 → 依存するカード群**の選択へ変える。
2. 自由文gapに、安定したID、複数依存、検証した版、根拠を補う。旧reasonは履歴として保持する。
3. `TESTED`とは別に、効果枝・召喚手順・実操作・歴史裁定・永続化の検証証拠を持つ。初回に既存statusを一括変更しない。
4. 歴史的なbatchの事実確認は固定fixtureに対して行い、現行coverageは最新差分の一般的な整合性検査で保証する。
5. 変更中は関連テスト、共有engine変更の完了時とリリース候補では全回帰。必要なgateを削る前に計測し、既存の検証規則との整合を明示して変更する。
6. 常時の「Astra → Coding → Astra全再監査」をやめ、契約作成者が引き続き実装できる小変更は同じcontextで完結させる。大きな契約変更のみ独立した観点でreviewする。

## 6. Recommended Development Architecture

### 実行系の上に、薄い分析層を置く

分析層が結ぶのは次の関係です。

**カードID／歴史版 → 効果枝・召喚手順の要件 → Capability契約 → 実装箇所・検証 → デッキ内の操作シナリオ**

最初は小さな表またはJSONで十分です。graph database、全JSの意味解析、巨大なontologyは不要です。実行時の状態・効果レジストリを二重化しません。

| 記録 | 最低限必要な内容 |
|---|---|
| カード要件 | 安定ID、歴史版、効果枝、召喚条件、必要な契約、出典と未確認事項 |
| Capability契約 | 入り口、事前条件、producer、状態／event、consumer、失効、永続化、対応範囲と反例 |
| 証拠 | 明示したtest ID、通した経路、期待値の根拠、実行結果、対象source hash |
| 実戦シナリオ | デッキ版、開始条件、プレイヤー入力、必要な契約、妨害分岐、終端条件 |

**1 module＝1 Capabilityにはしません。** 同じmoduleが複数契約を実装し、一つの契約が複数moduleを横断して構いません。

System02を完成済み契約の例にすると、「装備」は広すぎます。適切なのは「有効な装備元が、UIDで結ばれた対象へ、上限値として追加攻撃の許可を供給する」です。その実装と証拠は次のように結びます。

| 契約の部分 | 現在の主な実装 |
|---|---|
| 装備状態の生成・整合 | `1N_grave_equip_v31.js`、`1E_equip_v15.js`、Action処理 |
| 元の有効性と到達先 | `continuousSources`、`continuousReaches` |
| 許可値の合成と失効 | `continuousAttackLimitV48`、`attackLimitV48` |
| 実際の攻撃拒否 | `canDeclareAttackV48`、攻撃Processor |
| 記録と復元の証拠 | 既存Journal/digest、System01/02専用テスト |

現在のmodule構造は、**漸進開発を続ける土台として十分**です。ただし全4996枚に必要な意味表現がそろったとは言えません。例えば召喚制限にはカード名による分岐があり、一般化の余地があります。選んだ契約で複数経路の実装重複が繰り返されると確認できた時に、共通の判定・適用境界を局所的に抽出します。ファイル再編を先行させません。

## 7. Recommended Workflow

1. **同じ正本を固定する。** source hashと機械集計を読んで開始し、変更のない過去ログを読み直さない。
2. **実戦の詰まりと未完了要件を選ぶ。** 最初はドラグニティ／レダメ系を使う。実デッキの40／15リストは添付にないので、テーマ関連カードの暫定シナリオと明記する。
3. **不足の種類を分ける。** engineにない、既存機能の接続欠落、カード実装待ち、検証不足、歴史裁定未確定、分析不足を区別する。
4. **代表例と反例で契約を決める。** コスト／対象／解決時選択、source消失、無効、controller移動、待機状態の保存等から、その契約で関係する軸を確認する。
5. **共有不足を最小実装し、同じ契約を使うカード群を実装する。** 別の不足を持つカードは、残依存を記録して無理に解禁しない。既存機能で足りるならengine追加をしない。
6. **正規の経路で受け入れる。** 直接resolveの単体試験に加え、召喚・発動・選択・チェーン・解決へ到達する試験を置く。新状態や継続処理にはReplay、Undo/Redo、別contextでのSaveLoadを対応付ける。
7. **閉じた契約の依存先だけ再評価する。** 全616枚・全4996枚を再推論しない。動作確認後にstatusを変更する。
8. **実戦シナリオと回帰を通してまとめる。** 共有engine変更は全回帰を完了させる。配布可能な単位でcheckpointとhandoffを作る。

優先順位は、まず実戦を停止させる問題、次に複数テーマに共通する不足、次に既存契約で処理できる群です。推定unlock枚数だけで巨大なSystemを選びません。代表デッキが通るたび、未検証の効果群・召喚方式から次のsliceを追加し、最後まで未着手の長尾が残らないようにします。

デッキ内カードの `TESTED` 比率だけでデッキ完成を判定しません。現データではレダメとファランクスはTESTEDでも、ヴァジュランダ等は未着手、ガジャルグ等はPARTIALです。これは必要な経路を調べる出発点であり、ユーザーの実デッキ完成率ではありません。

## 8. AI / Tooling Strategy

**4996枚すべてに、同じ深さのAI推論を繰り返す必要はありません。ただし全カードの要件を確認対象から外すこともできません。**

| 担当 | 任せる仕事 | 任せない判定 |
|---|---|---|
| 決定的ツール | ID照合、status差分、登録一覧、manifest確認、test結果、hash、依存先抽出、計測 | カード本文だけから歴史裁定の正しさを確定すること |
| parsing／static analysis | API利用・直接状態書込み・登録経路・既知template候補の抽出 | 任意のJSについて意味上の完全対応を証明すること |
| 低コストモデル | 候補分類、類例検索、既知schemaへの下書き、不明点の抽出 | timing・裁定が曖昧なままTESTEDへ昇格すること |
| coding model | 契約・変更範囲・受入試験が確定した実装、定型展開 | engineの意味変更を実装中に独断で追加すること |
| 高推論モデル | lifecycle、発動／解決、trigger/timing、歴史裁定差分、複合依存、根本原因、設計review | 集計や同じ定型カードの毎回の再解釈 |

**モデル切替は仕事が十分大きい時だけ。** 小さなSystem02型変更なら、契約を理解した同じモデルがコードと検証まで担当する方が安い可能性があります。引継ぎ資料の作成・読込み・差戻しも含めた総費用で評価します。

受渡しは、baseline hash、契約と歴史根拠、関係する関数、代表カード、反例、テスト、未解決事項、変更可能範囲に限定します。ファイル全文や過去会話を毎回渡しません。一般的な日常実装では単一の担当contextを基本にします。

template生成は、代表例と反例を検証済みの狭い群で開始します。生成物は既存JS APIへ出力する案を優先し、新DSL runtimeは追加しません。召喚素材、対象性、任意when、同時処理、後年エラッタはtemplateの一致条件から外せない差分です。不明な形は自動処理から退避します。

歴史裁定は「2011年の採用仕様」「根拠URL／資料」「適用時期」「現在テキストとの差」「確実／未確定」を共有記録します。共通裁定は一度調べ、カード固有の例外だけ追加確認します。現行の公式記載やEDOProの挙動だけで当時の裁定を確定しません。

## 9. ENGINE_GAP Management

**616は阻害されているカード数として残す価値がありますが、開発バックログの単位には不十分です。**

今回、現616枚はすべて旧620件の監査行へ対応しました。旧分類を残存カードに再集計すると、27分類中26分類にカードが残っています。上位はprovenance 97、hidden_choices 97、battle_events 61、effect_gate 48です。

これは**現在不足しているCapabilityが26種類であるという意味ではありません。** 主分類には複数の不足が混在し、既存機能の範囲も更新されています。真の不足数は未確定です。全件の深い再監査を始めるのではなく、この既存索引を粗い入口として再利用します。

各効果枝は、複数の要求契約に依存できるようにします。「AとBの両方が必要」と「Aまたは代替Bで実現可能」を区別し、依存の循環があれば関連する契約を一つの作業単位にまとめます。

| 原因区分 | 意味 |
|---|---|
| ENGINE_MISSING | 必要な共通の意味・状態・適用経路がない |
| INTEGRATION_MISSING | 要素はあるが、必要な入口からconsumerへ接続されていない |
| CARD_WORK | 契約は足りるがカード側の仕事が残る |
| VALIDATION_MISSING | 実装はあるが必要な証拠がない |
| RULING_UNRESOLVED | 1103の採用仕様を確定できていない |
| UNKNOWN | まだ正しく分類する証拠がない |

これらは初期には別の分析欄です。既存statusを一括置換しません。gap理由は契約ID、対象の変種、失敗する経路、確認したsource hashへ結びます。依存する実装が変わったら該当行だけを「再確認必要」にします。自動的に解決済みとはしません。

進捗は、旧cohortで実際に解禁した枚数、新発見gap、再開したgapを別表示します。分類精度が上がるとgap総数が増えても、開発が後退したとは限りません。

対象残量にも補正が必要です。

|---|---:|---|

**616＋1307＝1923枚だけを残りと扱えません。少なくとも2303枚がTESTED／GENERIC_OK以外にあります。** さらに既存TESTEDの統合・歴史精度の負債は、この2303枚には含まれません。

## 10. Expected Benefit

### 確認できた事実

- 分類・recovery・Unified Effect・AI packは既存資産としてあるため、分析層はゼロから作る必要がない。
- System02はengine1ファイルのconsumer拡張でTESTEDを2枚増やした。内訳はgap1枚と未着手1枚。大規模再設計が常に必要という仮説は支持されない。
- System01は旧Cycle66からTESTEDを5枚増やし、gapを3枚減らしている。ただしSystem01/02の作業時間・AI料金の対照値はなく、速度優位の証明ではない。
- 現行scannerと実操作試験の保証範囲に差があり、完走KPIの追加が必要。
- Journalは2000件を超えると先頭を切り詰め、truncatedを記録する。長い一戦を最初からReplayする目標に対し、境界条件として検証対象になる。

### 期待する効果／未計測

- 同じ不足をカードごとに再発見するAI計算と、同じengineの再読込みを減らす。
- 既存Capabilityを再発明せず、producer／consumerの接続だけで済む仕事を見つける。
- 定型カードの展開を安くし、高推論を非定型の境界へ集中する。
- status固定値や過去batchの例外修理を減らす。
- 枚数が少ない変更でも、主要なデュエル経路を早く成立させる。

「何倍速い」「何日で4996枚完成」とは見積もれません。pilotでは**AI費用25%以上削減、同じ受入成果までの作業時間20%以上短縮**を採用目標に置きます。これは予測実績ではなく、方式変更に値する最低差として定める数値です。

KPIの優先順は、①裁定・回帰の品質条件、②正確な実戦完走率と完走までの開発時間、③主要デッキのシナリオ改善、④契約の完成とgap解禁、⑤TESTED増加です。実行時性能は別指標として、入力応答の遅延・停止もシナリオで測ります。

ENGINE completenessはmodule本数や単純な百分率にしません。「必要と確認した契約のうち、範囲別の受入試験を通った数／未検証／不足」を出し、未発見要件が残ることを表示します。

## 13. Pilot Experiment

### 目的と設計

**同じSystem02正本、同じ課題、同じ受入条件で、現方式Aと推奨方式Bを比較する。今回は設計のみで、実験は実行しません。**

課題は未完了12枚の候補集合から構成します。最終選定はpilot着手時に固定し、今回の監査では各カードの実装可能性を確定したふりをしません。ドラグニティ／レダメ関連と少なくとももう1テーマを含み、候補集合にはENGINE_GAP、NOT_STARTED、PARTIAL、IMPLEMENTEDを含めます。

その中から、共通の不足1件に関係する**主対象4枚（元ENGINE_GAPを2枚以上含む、2テーマ以上）**と、残依存・別の効果差を調べる8枚を固定します。既に完成したSystem02の2枚は回帰対照に使えますが、成果増分には数えません。条件を満たす集合が作れなければ、選定不成立として報告し、易しい課題へ黙って差し替えません。

共通の課題設定と受入仕様作成の費用も記録し、両方式のend-to-end費用に同じ条件で含めます。Bだけが作る契約表・依存関係・toolingはBへ計上します。Aにも元の既存クラスタ監査と資料を渡し、現方式を意図的に不利にしません。

### A/Bの運用

| 条件 | A：現方式 | B：推奨方式 |
|---|---|---|
| 作業の進め方 | カードを調べ、必要に応じ既存方式のSystem追加・tests・checkpoint | 共通契約と依存先を先に確定し、共有不足とカード群を閉じる |
| 正本・元資料 | 同じSystem02、同じ資料 | 同左 |
| 最初のモデル条件 | 同じモデル、同じ推論設定 | 同左。最初はworkflow差だけを測る |
| 作業環境 | 独立した作業コピーとcontext | 同左。途中の解決策を共有しない |
| 予算 | 1方式あたり実作業8時間上限、AI費用上限も事前固定 | 同じ上限。分析層準備を含む |
| 停止 | 固定受入の達成、または予算到達 | 同左 |

外部検索資料は共通の記録へ残し、実行順とcacheの有無も記録します。AI応答待ち、test待ち、人の待ち、実作業時間を分け、総経過時間も別記します。一つの担当がAで得た解決策をBへ持ち込む比較は避けます。

### 共通の受入成果

- 主対象4枚の全効果枝と必要な召喚手順が正規経路で通る。元gapの2枚以上が動作証拠付きで解禁される。
- 共通不足1件を、少なくとも2テーマで閉じる。カード名での専用engine分岐を増やさない。
- 固定したデッキ／入力列で、初期配札からルール上の終端まで少なくとも1戦が完走する。盤面の手修正・直接resolve・途中の状態注入による迂回を使わない。テスト開始時のfixture設定とは区別する。
- その対戦と指定分岐で、妨害、対象／sourceの移動、選択待ち、チェーン待ち、ターン遷移を確認する。これらは課題に関係する形で事前に固定する。
- 開始からの非空Replayで全Actionと最終digestが一致し、Undo/Redo後の分岐、別contextでのSaveLoad後の続行が正しい。2000Action境界は独立した受入項目として保持する。
- full regressionと配布buildが通る。実UIでも選択・再開・終端の到達を確認する。VM内のUI stubだけでUI完了を判定しない。

もし既存の別blockerによって一戦完走の受入がpilotの共通範囲に収まらなければ、実験開始前に「局所経路pilot」へ明示的に範囲変更できます。その場合、一戦完走や本格移行のGoとは報告せず、実戦統合pilotを別途必要とします。

### 測定項目

| KPI | 定義 |
|---|---|
| AI compute | 全モデルの入力・出力・取得可能なreasoning／cached tokenと、その実料金。引継ぎ・review・失敗試行を含む |
| elapsed work | 固定受入までの実作業時間、AI待ち、test時間、総経過時間を別々に記録 |
| ENGINE_GAP reduction | 最初に固定したcohortから動作受入を通った解禁数。新発見gapを別表示 |
| TESTED increase | 既存定義での増分と、新しい明示受入に合格した枚数を併記 |
| rework | 契約受入後の仕様やり直し回数と時間、差戻し回数 |
| regressions | 新たな失敗・裁定不一致・Replay不一致と修正時間、最終の未解決数 |

可能なら測定単位は「同じ受入成果までの費用・時間」とします。片方が上限未達なら、無理に速度比を出さず、上限時点の受入達成状況を示します。TESTED枚数で割っただけの比較を主指標にしません。

最初の1組で不利なら打ち切ります。有利なら別の共通不足・別のカード群で2組目を行い、担当または実行順を入れ替えて再現性を確認します。workflow採用後に、Bを固定したままモデルroutingだけを変更して費用差を測ります。最初からworkflowとモデルとcheckpoint頻度を同時に変更して、効果の原因を混同しません。

## 14. Go / No-Go Criteria

**Goは以下をすべて満たす場合です。**

1. 品質条件：同じ受入を達成し、最終の新規回帰0、Replay不一致0、既知の歴史裁定不一致0、未解決の重大問題0。未確定裁定を暗黙に合格扱いしない。
2. 成果条件：主対象4枚、元gap2枚以上、共通不足1件、2テーマ以上、一戦完走と永続化の受入を達成する。
3. 効率条件：Bの準備・tooling・handoffを含むAI費用がA比25%以上少なく、同じ受入までの実作業時間が20%以上短い。Aが時間上限まで未達なら、観測できた費用・時間の上限／下限から、この条件を示せる範囲に限定する。
4. 手戻り条件：Bのrework時間と人の介入時間がAを上回らない。
5. 再現条件：2組目でも品質と効率の改善方向が再現する。採用の集計は両組の総費用・総作業時間で行い、重大な悪化例を平均で隠さない。

一組だけ良好なら、Goは次の限定pilotまでです。全4996枚の一括移行を承認する根拠にはしません。

**No-Go／見直し**は、準備4時間の目安を超えても対象契約が確定しない、実戦改善がない、必要な資料が毎回全面再生成になる、同じ受入で費用・時間が改善しない、または品質条件を満たせない場合です。

その場合も動作を改善したpatchや有用な証拠を捨てる必要はありません。自動生成器や過剰な分類を縮小し、Card-firstに明示的なテスト証拠と小さな共有契約だけを取り入れた形へ戻します。全面rewriteへ自動的に移行しません。
